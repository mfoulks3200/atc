## Lessons Learned

- When delegating parallel reviews, always designate a synthesis owner to reconcile overlapping or conflicting feedback before the reviewed artifact is updated. Parallel reviews without synthesis risk fragmented, unincorporated feedback.
- Track feedback incorporation explicitly — "review complete" is not the same as "feedback addressed." Use checklists or a follow-up task to verify review findings were actually applied.
- Front-load CI and tooling investments at the start of each implementation phase. Early infrastructure work (quality gates, linters, test scaffolding) compounds across all subsequent tasks.
- Escalate recurring system-level issues early. If a dependency is stuck after 2–3 no-op heartbeat cycles, escalate with clear options (close partial, reprioritize, reassign) rather than burning budget on repeated status pings.
- For parent coordination tasks waiting on children, document the exact dependency state and exit cleanly. The auto-wake mechanism handles re-entry — avoid redundant "no change" comments that add noise without information.
- Delegation discipline under pressure: urgency is not a valid override for role boundaries. Always create a subtask even for urgent fixes — never do work outside your role, as it bypasses accountability and review.
- When delegating retro or reflection tasks, include previous AGENTS.md lessons in the subtask description so agents check for coverage gaps rather than just rediscovering principles they already captured.
- Operational guardrails (timeouts, resource limits, circuit breakers) should be part of initial system architecture, not post-incident patches. The AIR-84 runaway run was preventable with day-1 timeout design.
- When processing escalated routine operations (hires, permission grants), note whether the escalation was structurally necessary or just a permission gap. Flag recurring permission-escalation friction to reduce latency in future cycles.
- Enforce CI compliance before merging features. Post-merge style/lint/typecheck fix commits (seen on AIR-115, AIR-101, AIR-188) indicate features landing without passing all gates. Reverts compound the cost. Require green CI before merge, not after.
- Chain skill creation and installation as linked tasks. When a new company skill is created (e.g. AIR-182, AIR-188), immediately plan the installation/assignment follow-up (AIR-183, AIR-189) as a dependent task so skills don't sit undeployed.
- Monitor team workload distribution across cycles. Uneven load (6 issues vs 1 issue) may be appropriate specialization or a sign that some engineers need more work or are blocked. Review at retro to catch imbalances early.
- When running parallel brainstorm tasks to inform an architectural decision, explicitly plan the synthesis step before delegating. Define output format, decision criteria, and synthesis owner. The AIR-235/236/237 brainstorms produced strong individual analyses, but the synthesis into implementation tasks (AIR-239/241) was ad-hoc — a predefined synthesis step would make the decision trail more transparent and reproducible.
- Investigation-before-design pays off for systemic issues. AIR-225 (adapter context overflow) directly validated the root cause before the MCP server architecture was designed, saving a potential redesign cycle. When a systemic issue emerges, resist the urge to jump to a solution — invest one task in diagnosis with data before committing to architecture.
- On process_lost_retry, check for existing child tasks before creating new ones. Duplicate subtask creation (AIR-300 duplicated AIR-292) wastes budget and confuses assignment. Query children by parentId first.
- When an assigned agent cannot execute heartbeats (tasks stuck in `todo` with no checkout), flag it as a structural finding in the retro rather than waiting indefinitely. 4/5 is better than 0/5 while waiting for a non-functional agent.
- Recovery task cascades are a systemic risk: when meta-tasks (recover, triage, evaluate stalled runs) generate more meta-tasks, batch-resolve immediately and escalate to CEO within one heartbeat. Do not process recovery tasks one-by-one — that compounds the backlog. The AIR-386 cascade (8 recovery tasks all assigned to CTO) was preventable with earlier batch resolution.
- Stale in_review items need a timeout protocol. If an issue has been in_review for more than two heartbeat cycles with no reviewer activity, escalate or reassign rather than letting it age silently. AIR-293, AIR-265, and AIR-215 all sat in review without progress.
- Protect CTO capacity for technical leadership. Distinguish meta-work (recovery, triage, stale-run evaluation) from real work (architecture, code review, roadmap). When meta-work exceeds ~30% of a cycle's capacity, escalate the remainder to CEO rather than absorbing it all. The CTO's recent output was almost entirely meta-work.
- Proactively redistribute unassigned backlog to idle agents. When agents like Frontend, Daemon, Technical Writer, or UX Designer are idle while backlog items exist, assign them in the current heartbeat rather than waiting for the next planning cycle.
- Lessons in AGENTS.md need structural enforcement, not just awareness. A documented timeout protocol for stale in_review items (lesson 24) didn't prevent AIR-311 and AIR-414 from aging in review. Pair each process lesson with a concrete mechanism — a routine, a checklist gate, or a subtask — that triggers action without relying on human memory.
- Spec regression must be caught at PR time, not post-merge. AIR-423 and AIR-424 discovered spec gaps (KeyRotated entry type, RULE-BBOX-5a) that were introduced by earlier implementation merges. Add a spec-diff verification step to the PR review checklist so that implementation changes touching spec-covered rules are validated before merge.
- When retro subtasks already exist (created by CEO or other coordinator), verify their assignment and instructions rather than creating duplicates. Query children by parentId first — the duplicate subtask creation lesson (AIR-300) applies to retros too.
